## 七、状态切换平滑化

**问题**：缩放时状态（0-8）瞬间跳变，连线/粒子/文字生硬切换。

**方案**：
1. **浮点状态 + smoothstep**：`drawFrame()` 中用连续浮点值 `sf`（0~8）替代整数 `zoomState`，每个视觉元素的 alpha 通过 smoothstep 在过渡带内渐变：

   | 元素 | 过渡区间 |
   |------|---------|
   | 连线 | 6.5 → 7.5 淡出 |
   | 中心环 | 6.8 → 7.5 淡出 |
   | 节点年份 | 5.2 → 6.0 淡出 |
   | 时钟粒子 | 6.5 → 7.5 淡入 |
   | 中心文字 | 7.5 → 8.0 淡入 |

2. **CSS zoomState 防抖**：整数 `zoomState` 仅在插值结束或每 15 帧更新一次，给 CSS transition 时间播放完。

3. **固定时长 ease-out 动画**：缩放插值从 lerp 改为 15 帧 cubic ease-out，70% 立即响应 + 30% 缓慢到位，状态浮点值在 250ms 内缓慢穿越过渡带。

## 九、连线与节点移动同步延迟问题（2026-05-11 调查）

### 问题描述

滑动屏幕（平移）和放大/缩小屏幕（缩放）时，Canvas 绘制的连线与 WXML 渲染的节点之间存在可见的移动延迟。全部节点和连线点亮后尤为明显。

### 根因分析

微信小程序采用**双线程架构**：

| 线程 | 职责 |
|------|------|
| JS 线程（逻辑层） | 执行 Page 方法、`setData()`、Canvas 2D API 调用 |
| View 线程（渲染层） | 接收 setData 数据渲染 WXML、执行 Canvas 绘制指令、合成画面 |

两者通过消息传递通信，存在天然的时序差异：

1. **`setData()` 立即发送**：调用后数据同步更新 `this.data`，并**即刻**将数据发送到 View 线程。
2. **Canvas 指令延迟发送**：Canvas 2D API 调用被**缓冲记录**，仅在 JS 事件循环 tick 结束时**批量刷新**到 View 线程。

因此每次触摸事件中：
- `setData({ offsetX, offsetY })` → View 线程先收到 → WXML 节点先更新位置
- `drawFrame()` 产生的 Canvas 指令 → View 线程后收到 → 连线后更新位置

**连线始终落后节点约 1 帧**，与 `drawFrame()` 的计算量无关（因此单纯优化绘制性能无效）。

### 尝试过的方案

#### 方案 A：显示缓冲区（display buffer）

在 `setData` 回调中更新 `_displayScale` / `_displayOffset`，`drawFrame()` 使用缓冲区值而非 `this.data.*`，试图让 Canvas 等待 WXML 渲染完成。

**结果**：无效。缓冲区引入额外 1 帧延迟，且 setData 可能合并多帧更新，反而加剧不同步。

#### 方案 B：触摸时快速路径（fast path during touch）

检测 `_isTouching` 标志，触摸期间 `drawFrame()` 仅绘制连线 + 年份，跳过所有粒子动效（500+ 粒子、渐变辉光），试图将 Canvas 绘制耗时压到 16ms 以内。

**结果**：几乎无改善。瓶颈不在 JS 计算，而在 JS→View 线程通信时序。

#### 方案 C：Canvas 移入 zoom-container（共享 CSS transform）

将 `<canvas>` 从 `.zoom-container` 外部移入内部，两者共享 CSS `transform: scale() translate()`。移除所有 draw 方法中的 `offsetX`/`offsetY`/`mapScale` 坐标计算，依赖 CSS transform 统一处理平移/缩放。

**结果**：
- ✅ **延迟完全消失**：平移时 Canvas 无需重绘，CSS transform 同时移动连线和节点，完美同步。
- ❌ **连线严重抖动**：动画循环每帧调用 `drawFrame()` 重绘 Canvas，与 CSS transform 的 setData 更新产生冲突。浮点动画中 `fx`/`fy` 每帧变化（Canvas 即时反映），但 WXML 节点每 4 帧才通过 `setData({ nodes })` 更新，两者不同频导致可见抖动。

**已回退**到 develop 版本。

### 解决方向

Canvas 移入 zoom-container 的方案在平移同步上完全解决了延迟问题，抖动源自动画循环的**重绘频率与 WXML 更新频率不匹配**。后续可能的改进方向：

1. **对齐重绘节奏**：动画循环中仅在 `setData({ nodes })` 的同一帧（每 4 帧）才重绘 Canvas，使连线与节点的浮点动画以相同周期更新。
2. **节点也走 Canvas**：将节点绘制也迁入 Canvas，彻底消除 WXML 与 Canvas 的双轨渲染，所有元素在同一个 Canvas 中完整绘制。代价是实现复杂度高，且失去 WXML 的 CSS 动画能力。
3. **仅缩放时重绘**：平移期间完全不重绘 Canvas（CSS transform 已处理），仅在缩放值变化或浮点动画更新 WXML 节点时重绘。


### 方案 D（2026-05-11 最终采用）：物理/显示分离快照

放弃 Canvas 移入 zoom-container，保持 Canvas 在原位。通过**分离物理模拟与显示数据**解决抖动：

1. **`_physicsNodes`**：独立于 `this.data.nodes` 的深层拷贝数组，每帧由 `updateNodes()` 更新浮动物理（fx/fy/vx/vy）。
2. **`this.data.nodes`**：每 4 帧从 `_physicsNodes` 创建 `Object.assign({}, n)` 快照，通过 `setData` 发送到 WXML。
3. **Canvas 绘制**：`drawFrame()` 及其子方法读取 `this.data.nodes`（冻结快照），与 WXML 渲染使用**完全相同的对象副本**。

**效果**：
- ✅ 抖动消除：Canvas 和 WXML 读取同一份冻结位置，不再有时序差
- ✅ 原有动效不受影响：所有粒子、辉光、连线渲染保持不变
- ✅ 代码侵入性小：仅改 `buildFromCloud`、`updateNodes`、解锁同步方法
- ⚠️ 延迟（~1 帧）仍存在：这是微信双线程架构固有问题（setData 立即发 vs Canvas 2D API 批量刷新），可接受

**涉及改动**：
- `buildFromCloud()`：初始化 `_physicsNodes` + 快照 `data.nodes`
- `updateNodes()`：物理跑在 `_physicsNodes`，每 4 帧 `Object.assign` 快照到 `data.nodes`
- `_applyUnlockFromCache()` / `refreshUnlockedStatus()`：解锁状态同时写入两个数组
- `_initClockParticles()` / `_initOrbitalParticles()`：使用 `_physicsNodes || this.data.nodes`

## 十、全 Canvas 单轨渲染（2026-05-11 最终方案）

### 问题回顾

方案 D 消除了抖动，但延迟（~1 帧）仍存在。后续尝试了多种方案试图消除延迟：

| 方案 | 做法 | 结果 |
|------|------|------|
| Canvas 移入 zoom-container + setTransform 逆变换 | Canvas 侧用逆矩阵抵消 CSS transform | 连线完全不被缩放，严重偏移 |
| 临时篡改 mapScale=1 | drawFrame 中 data.mapScale 临时置 1，让 draw 方法输出原始坐标 | 仅 state 4（scale=1）正常，其余状态偏移 |
| 延迟 setData | 用 setTimeout 延迟 WXML 节点更新，等 Canvas 追上 | 线先动或节点先动，无法稳定对齐 |

### 根因

**WeChat Mini Program 的 Canvas 2D（`type="2d"`）使用原生渲染管线，不经过 CSS transform。** Canvas 内容渲染到独立原生纹理，合成在 WXML 视图层之上，祖先元素的 CSS `scale()`/`translate()` 对 Canvas 内容无效。

因此，只要节点（WXML）和连线（Canvas）分属两个渲染系统，任何依赖「时序对齐」的方案都无法稳定工作。

### 解决思路

**双轨变单轨**：将节点圆点、文字标签全部迁入 Canvas，与连线、粒子在同一上下文渲染。WXML 仅保留触摸热区和控制按钮。

这是用户提出的思路转换：节点之间从未出现延迟，线和线之间也从未出现延迟，问题仅存在于节点（WXML）和线（Canvas）之间。把它们变成同一种东西即可。

### 具体改动

**cloud.wxml**：删除 `zoom-container` 和所有 `star-node` 元素，Canvas 直接接收 touch 事件。

**cloud.wxss**：删除全部节点/文字/呼吸动画 CSS（~200 行），仅保留页面布局和按钮样式。

**cloud.js**：

| 新增方法 | 说明 |
|----------|------|
| `drawNodes(ctx)` | Canvas 绘制 9 个节点圆点。四种样式：暗态（7rpx 半透灰）、点亮（9rpx 白光蓝辉）、中心暗态（11rpx 半透）、中心点亮（17.5rpx 微金双层辉光）。正弦呼吸动画替代 CSS keyframes |
| `drawNodeLabels(ctx)` | Canvas 绘制文字标签。遵循原 zoomState 显示规则（0-4 全显 / 5-6 仅中心 / 7+ 隐藏），字号、颜色与偏移匹配原 WXSS |
| `_onCanvasTap(tx, ty)` | 屏幕坐标 → 世界坐标逆变换，检测最近节点，点击跳转章节。替代原 WXML `onStarTap` |

| 修改 | 说明 |
|------|------|
| `drawFrame()` | 新增 `nodeAlpha`（7.6→8.0 淡出）、`labelAlpha`，调用 `drawNodes()`、`drawNodeLabels()` |
| `handleTouchStart/Move/End` | 触摸事件从 zoom-container 移至 Canvas。直接赋值 `this.data.*` 替代 `setData`（无需 View 线程通信）。`handleTouchEnd` 新增 tap 检测逻辑 |
| `drawNodes()` state 7 特殊处理 | `zoomState >= 7` 时跳过中心节点，仅绘制外侧八节点 |

| 删除 | 说明 |
|------|------|
| `_scheduleSyncSetData()` | 不再需要延迟 setData 对齐 WXML 渲染 |
| `onStarTap()` | 被 `_onCanvasTap()` 替代 |
| WXML 节点渲染体系 | `zoom-container`、`star-node`、`star-core`、`star-text` 全部移除 |

### 效果

- ✅ 延迟彻底消除：所有视觉元素在同一 Canvas、同一帧、同一坐标系渲染
- ✅ 抖动消除（方案 D `_physicsNodes` 快照保留）
- ✅ 原有动效完整保留：粒子、辉光、呼吸动画、连线三层渲染、状态平滑切换
- ✅ 9 个 zoomState 行为不变：标签显隐、连线淡出、粒子淡入、节点淡出规则均与原 WXML 一致
- ✅ 节点点击跳转正常：Canvas 坐标逆变换检测
- ✅ 代码侵入可控：新增约 150 行，删除约 200 行

### 关键经验

> **跨渲染系统的同步问题是物理定律，不要试图用时序 hack 绕过。把需要同步的元素放在同一个渲染系统里。**
